# Recovery parity and Windows reserved-stack follow-up

Follow-up: [whole-compilation worker and recursive lowering](recursive-lowering.md).

2026-10-22. Follow-up to [recursive descent](parser-recursive-descent.md) and
[reserved stacks](parser-reserved-stack.md). Parser changes measured here are
at `c9fbaccf`; Linux collection commands are at `333c4904`. Native runner
harness source is `32fb7b0a`; the serial collector and analysis commands are
tracked alongside this report.

**All ten recorded recovery differences are fixed.** Both release and debug
match the frame machine on the 150-case grammar corpus and 50 broader inputs
across every tested mode. Linux reserved-stack Lua parsing takes 23.189 ms release
and 120.428 ms debug: 36.6% and 25.2% below the feature-disabled production
baseline in this cohort. The production parser remains the frame machine.

**Native Windows confirms demand commitment in release and debug.** A 100 GiB
reservation starts with 8 KiB writable and handles 65,536 live page frames.
Reserved RD uses 30.5% / 46.7% less release parser time on the expression /
statement mixes; debug reductions are 22.1% / 31.5%. Recovery, corpus parity,
and 16,384-level parser probes pass. Timings exclude worker launch and are noisy.
GNU x64 ran natively; MSVC has only cross-checks. This supports evaluating a
reserved worker, while retaining the frame machine until API/resource policy
is decided. It establishes a speed opportunity, not a general memory win.

## What the ten differences were

The original baseline snapshots remain in
`parser-reserved-stack-data/reserved-{release,debug}-grammar.json`.
The sources are generated by `scripts/parser_study_cases.py`; every malformed
function has a following `return` and file-scope declaration so accidental input
consumption is observable. These are ten failing cases, not ten independent
root causes.

| Case suffix (`bad-*.c`) | Prototype behavior before this follow-up | Repair now matched to machine |
| --- | --- | --- |
| `stray-operand-group` | Ends `(a b)` at `a`, leaks `b)` into later statements | Reports stray operator position, skips to owned `)`, marks operand recovered |
| `mismatched-close` | Leaks unowned `]` into a separate null statement | Expression owner diagnoses and consumes stray closer |
| `missing-call-comma` | Closes call early, leaks remaining arguments | Diagnoses missing separator and retains subsequent arguments |
| `if-empty-condition` | Builds an error-expression, generic message | Missing expression slot and `if`-specific message |
| `if-stray-operand` | Treats stray operand as then-body; detaches else | Synchronizes to header `)`, retains then/else |
| `if-missing-body` | Missing then-body consumes `else` | Missing body leaves enclosing if's `else` unconsumed |
| `while-header-brace` | Omits operator diagnostic/recovered flag in body | Matches expression owner and statement-boundary repair |
| `do-missing-while` | Consumes following assignment as condition | Missing condition; following assignment remains a statement |
| `for-extra-clause` | Extra separator becomes null loop body | Bounded scan skips extra header clause through owned `)` |
| `switch-condition` | Leaks stray operand and closes switch scope early | Header synchronization retains switch body and label ownership |

The implementation reuses expression-frame recovery with an already built
operand, pooled storage, and the original error count. It does not rewind,
reparse, or duplicate the successfully built subtree. An explicit marker avoids
running the same recovery twice after a hybrid handoff. Recursive statement
calls and frame handoffs now carry `else` ownership; compounds start fresh.
Missing header operands use `ExpressionSlot::Missing`. The `do` repair uses the
existing diagnostic variant, and the `for` repair shares the frame's bounded
lookahead scanner. Production grammar behavior is unchanged.

The regression test also checks nested then-bodies through `while`, `for`,
`do`, labels, and nested `if`, missing conditions for each header family, a
missing `while` with a visible parenthesized condition, and multiple missing
call commas. It compares complete rendered AST/provenance/diagnostic output
at every hybrid threshold 0 through 16, plus recursive and growing modes.

## Stack cost of recovery parity

An intermediate recovery implementation kept a large `ExpressionFrame`
temporary live in every recursive expression call. Stack sampling caught a
regression to 1,152/2,848 B per parenthesis level release/debug. Completion is
now outlined into `#[inline(never)] rd_finish_expression`, called after descent
returns. It seeds the existing recovery frame without keeping its storage live
through descent. This materially reduced that regression.

| Input shape | Original release B/level | Final release | Original debug B/level | Final debug |
| --- | ---: | ---: | ---: | ---: |
| Parentheses | 704 | 736 | 1,952 | 2,240 |
| Nested blocks | 1,008 | 1,024 | 8,176 | 8,512 |

Final slopes use the address-span difference between depths 4,096 and 16,384,
with separate instrumented runs. They measure parser grammar entry addresses,
not an exact native-stack peak. At 16,384 levels, reserved-stack post-parse RSS
is 11.52 MiB release / 35.04 MiB debug for parentheses and 16.02 / 133.04 MiB
for blocks. Reservations are 100 GiB in these Linux samples; initial stack RSS
is 16 KiB release / 48 KiB debug. All eight samples finish with no diagnostics,
no hybrid fallbacks, no major faults, no swap, and no huge-page backing.

Recovery parity therefore has a measurable native-stack cost, especially in
debug. The Windows 1 MiB default stack remains unsuitable for unrestricted raw
recursion. A large reserved worker or an explicitly bounded hybrid is required.
The reservation is finite, and OS exhaustion remains a process/runtime failure,
not a normal parser-limit diagnostic.

### Reservation and demand commitment

The actual worker uses `CreateThread` with
`STACK_SIZE_PARAM_IS_A_RESERVATION`. Windows manages commitment behind its
moving guard; the implementation installs no exception handler and never moves
the stack. `VirtualQuery` measures writable committed regions, excluding the
guard. This is commitment, not physical residency.

| Page-frame probe | Debug | Release |
| --- | ---: | ---: |
| Initial writable commitment, 1 GiB reservation | 8,192 B | 8,192 B |
| Initial writable commitment, 100 GiB reservation | 8,192 B | 8,192 B |
| Native stack bytes per live frame | 4,384 | 4,208 |
| Address span at 65,536 frames | 287,314,015 B | 275,779,687 B |
| Deepest writable commit, 1 GiB reservation | 287,318,016 B | 275,783,680 B |
| Deepest writable commit, 100 GiB reservation | 287,322,112 B | 275,783,680 B |
| Undersized 1 MiB and 64 MiB children | Both `0xC00000FD` | Both `0xC00000FD` |

Each page-probe call keeps a 4,096-byte array live. Both reservations finish
at depths 0, 256, 4,096 and 65,536. These are page frames, not parser grammar
levels. Commitment remains after unwinding until the thread exits. The two
negative probes use depth 4,096 on 1 MiB and depth 16,384 on 64 MiB. Each child
runs through `scripts/cargo_runner.py` to suppress desktop crash dialogs; the
parent verifies stack-overflow evidence and passes. The Wine-only release exit
101 described below does not reproduce in either native profile.

Each profile passes 684 timing samples, 17 real-corpus parity checks and four

Deep parser runs sample grammar-entry addresses at 4,096 and 16,384 parenthesis

### Native measurement limits

- Native GNU x64 execution only; no native MSVC run.
- No staged Lua fixture in the clean Actions checkout; Linux Lua numbers do not
  imply Windows Lua performance.
- No CPU isolation. Desktop activity and other work can affect timings; ranges
  and CVs are reported rather than treating all deltas as deterministic.
- Windows process RSS, physical stack residency, page faults and hardware
  instructions/cycles are unavailable in this harness. Zero-valued RSS/fault
  fields mean unavailable, not zero consumption. Writable commit and arena
  requests are measured.
- Worker creation/join is excluded and not independently measured on Windows.
  A fresh worker per tiny file may erase phase-7 savings.
- This native cohort rotates modes in one process, unlike the fresh-process
  Linux cohort. Their timings are not pooled.

## Recommendation and remaining decisions

Keep the default frame machine while evaluating reserved-worker integration;
recovery parity is no longer a known blocker on the measured corpus. The Linux
speed improvement survives the recovery fixes. The reserved stack remains a
credible way to preserve simple recursive expression/statement control flow,
with a large memory cost for pathological debug nesting. The bounded hybrid is
still the option that limits native stack consumption.

Before changing the default, decide a reservation/resource policy and how to
preserve parser-limit diagnostics near exhaustion. A finite reserved stack can
still terminate the process; it does not preserve the frame machine's arbitrary
nesting guarantee. The bounded hybrid preserves an iterative fallback.

Also decide whether worker ownership of the full preparation/parse arena lifetime
fits the production API: the callback and result require `Send`, and existing
arena/context values cannot simply cross threads. Preparation inside the worker
is what this prototype measures. Reusing frame recovery and declaration/extension
handoffs means it still needs those frames; this study does not justify deleting
the production expression/statement machinery. Measure end-to-end worker cost
on representative Windows files before choosing a per-file worker design.
