Double-E × bcc-rust
Feasibility audit · 2026-08-21

Whole-parser stack-machine integration study

Build the whole parser as an explicit stack machine.

Double-E should remain the precedence-reduction engine for expressions—and potentially declarators—inside a larger non-recursive pushdown parser. Declarations, statements, initializers, and translation units become resumable grammar frames on a control stack. bcc-rust already contains an integrated Double-E evaluator in its preprocessor, making this an extension of an existing design rather than a foreign architecture.

Recommendation
Proceed

Use one parser driver, an explicit control stack, specialized grammar frames, and shared Double-E reduction machinery.

01 / VERDICT

A unified pushdown machine is feasible—and better aligned with the project

Executive finding

Double-E directly addresses precedence-driven subgrammars. The surrounding C grammar can also avoid recursion, but it needs a second mechanism: an explicit stack of phase-oriented frames. Each frame consumes a token, pushes a child frame, reduces a completed child into its parent, reprocesses lookahead, or enters recovery. The result is one non-recursive parser machine without pretending that every grammar production follows the Unary/Binary expression invariant.

The two-state loop maps cleanly onto C tokens

Unary state

A token is interpreted as a prefix operator, grouping/type construct, or primary operand.

  • Push prefix operators: !, ~, *, &, unary +/-, ++/--
  • Push a grouping marker for (
  • Create an AST node for literals and identifiers
  • Delegate casts, sizeof, and compound literals to type-aware helpers

State B / expecting operator

Binary state

A token is interpreted as postfix syntax, an infix operator, a closing delimiter, or an expression terminator.

  • Reduce by precedence, then push infix/assignment operators
  • Handle calls, subscripts, member access, and postfix ++/--
  • Match ), ], and the ?/: pair
  • Stop before caller-owned tokens such as ; or a top-level delimiter

Unbound prefix, postfix, infix, grouping, call, subscript, and conditional markers—with precedence, arity, associativity, and source location.

operand_stack: Vec<ExpressionIndex>

References into bcc-rust’s expression arena. Each reduction creates an AST node, stores it, and pushes its index back.

03 / IN-TREE PROOF

The preprocessor already runs a production-integrated Double-E machine

This is not just a resemblance

bcc-rust’s PreprocessorExpressionParser contains the defining structure directly: Unary/Binary states, precedence and associativity, separate operator and operand stacks, and a reduction loop over preprocessor tokens.

  • Twenty-six operator/marker variants cover unary, arithmetic, shift, relational, equality, bitwise, logical, ternary, comma, and grouping forms.
  • The operand stack preserves signed versus unsigned integer behavior.
  • The evaluator is already connected to Context, source vectors, token conversion, and structured diagnostics.
  • State and stacks are reset and reused between #if/#elif expressions.
  • A compact typed configuration selects C99 plus an allow/warn/deny extension policy; comma diagnostics use operand liveness so short-circuited subexpressions remain unevaluated.
  • The outer preprocessing adapter yields Result<Token, TranslationError>, preserving source provenance while diagnostics bubble to the caller; only the executable boundary renders them.

06 / TARGET DESIGN

One pushdown parser, multiple specialized frame machines

Input

Buffered token cursor

Wraps the existing preprocessor, owns lookahead/reprocessing, and exposes typed tokens with source vectors.

→
Control

ParserMachine

Runs Vec<ParseFrame>. The top frame consumes, pushes a child, reduces a value, reprocesses lookahead, or recovers.

↔
State + output

Arenas and scopes

Expression, statement, declaration, declarator, list, and error nodes plus a scope-aware typedef/tag/symbol stack.

“Stack machine for the whole parser” should mean one explicit control stack—not one enormous operator stack. Expression frames use Double-E’s Unary/Binary reducer. Declarator frames may use a constructor reducer. Keyword-led declarations and statements use phase enums. All of them share the same driver, tokens, values, diagnostics, and recovery protocol.
enum ParseFrame {
    TranslationUnit(TranslationUnitFrame),
    ExternalDeclaration(ExternalDeclarationFrame),
    Declaration(DeclarationFrame),
    Declarator(DeclaratorFrame),
    TypeName(TypeNameFrame),
    Initializer(InitializerFrame),
    Statement(StatementFrame),
    Expression(ExpressionFrame),  // owns Double-E operator + operand stacks
}

enum ParseAction {
    Consume,
    Push(ParseFrame),
    Reduce(ParseValue),
    Reprocess,
    Recover(SynchronizationSet),
}

while let Some(frame) = machine.frames.last_mut() {
    match frame.step(machine.tokens.lookahead(), &mut context) {
        ParseAction::Push(child)   => machine.frames.push(child),
        ParseAction::Reduce(value) => machine.finish_frame(value),
        action                     => machine.apply(action),
    }
}
07 / BCC-RUST CHANGES

The AST and parser contract need repair before the machine lands

MODEL 01

Resolve expression typing later

Expression.result_type: TypeIndex assumes type information at parse time. Make it optional/unresolved or move types to a semantic side table.

MODEL 02

Add source spans

Store SourceVectors on expression nodes or in a parallel arena. Stack operators need their originating token span for useful errors.

MODEL 03

Fix argument storage

Call.arguments: VectorSlice<Expression> cannot safely describe interleaved arena nodes. Add a separate Vec<ExpressionIndex> list arena.

MODEL 04

Define TypeName

Casts, compound literals, and sizeof(type) already reference this missing type. Implement a working parse_type_name helper.

MODEL 05

Add member access

The current expression model has no explicit . or -> node/operator. Add member and indirect-member variants with an identifier field.

MODEL 06

Make typedef lookup real

The parser owns a typedef map but never inserts into it. Cast/grouping disambiguation depends on correct scope-aware typedef binding.

STACK 07

Define the frame protocol

Every frame must express consume, push-child, reduce, reprocess, and recover actions without holding invalid borrows across driver iterations.

STACK 08

Buffer the token cursor

Replace ad hoc one-token pending state with explicit lookahead and reprocessing owned by the machine. Frames must never secretly consume caller delimiters.

STACK 09

Type the reduction values

ParseValue must carry expression, statement, declaration, declarator, type-name, initializer, and list results back to parent frames safely.

RECOVERY 10

Add error nodes and sync sets

Synthetic nodes plus per-frame delimiter/keyword synchronization let the machine unwind or resume without recursive error propagation.

SCOPE 11

Make scope transitions explicit

Compound/function frames push and pop scopes. Typedef-name lookup must be correct before choosing declaration versus expression frames.

BUILD 12

Restore the parser build

The current module has 14 errors unrelated to the new machine. Repair its missing arenas, result types, diagnostics, and incomplete return paths first.

What the two implementations demonstrate

  • A compact two-state control loop in Rust.
  • Operator precedence and left/right associativity mechanics.
  • Grouping parentheses without recursive expression descent.
  • Integration with bcc-rust tokens, source vectors, signedness, and diagnostics.
  • Basic conditional, call-marker, and fixed-arity bookkeeping.
  • A concrete base for extracting a reusable reduction kernel.

What still needs to be demonstrated

  • AST construction and source-range preservation.
  • A safe ParseFrame push/reduce/resume protocol.
  • The complete C operator set and language-parser comma/call distinction; the demo intentionally does not implement comma expressions.
  • Non-recursive declarations, declarators, type names, initializers, and statements.
  • Scope-aware declaration-versus-expression selection.
  • Whole-parser recovery without frame leaks, invalid reductions, or panics.
09 / RISKS

The hard parts move from recursion into explicit frame design

One giant Double-E machineHighForcing keywords, declarations, and statements into Unary/Binary operator semantics would create opaque special cases. Keep one driver but distinct frame state machines.
Frame-state explosionHighEvery recursive function becomes phases plus stored partial results. Generate a grammar/frame inventory first and keep phase enums local to each production family.
Type-name ambiguityHigh(T) x is a cast only when T is a type name in the current scope. This requires working typedef binding before expression parsing can be correct.
Delimiter/comma contextHighArguments, grouped comma expressions, subscripts, conditional middles, declarations, initializers, and caller stop tokens all reuse punctuation differently.
Error recoveryHighA frame machine must preserve control-stack invariants while synchronizing. Each frame needs explicit owned delimiters, expected child values, and a legal unwind boundary.
AST contractHighThe current expression model is incomplete and assumes result types too early. Integrating first would lock in awkward representation choices.
Conditional associativityMediumThe prototype’s nested-ternary failure shows that ? must be a blocking marker and : must convert it into a separate right-associative ternary operator.
Rust borrowingMediumA frame cannot remain mutably borrowed while pushing another frame or mutating arenas. Returning a small owned ParseAction from each step avoids self-referential control flow.
PerformanceLowThe machine remains linear in consumed tokens with heap-backed memory proportional to grammar nesting and operator depth—well aligned with the project’s arenas.
Reference-code licenseMediumThe author’s fuller Draconum source explicitly grants no permission to use, modify, or share it. Do not copy that code. The local Rust repository also has no license file; clarify provenance before redistribution.
Reference completenessMediumThe article describes broad C support, but the published C# reference still throws NotImplementedException for . and ->. Treat it as guidance, not a complete oracle.

11 / ACCEPTANCE

Minimum evidence before calling the stack-machine parser complete

The grammar uses no recursive parser calls

Every nested construct must be represented by a heap-backed frame. Deeply nested valid and invalid inputs must not overflow the Rust call stack.

Frame ownership is deterministic

Trace tests must show which frame consumes each token, which delimiter ends it, and which typed value it returns to its parent.

Every C99 operator has a golden AST test

Include equal-precedence and right-associative chains, not just isolated operators.

Nested ternary works in both branches

Cover a ? b ? c : d : e and a ? b : c ? d : e.

Comma roles are distinguishable

Prove f(a,b), f((a,b)), and nested mixtures produce different ASTs/argument counts.

Postfix chains compose

Cover shapes such as (*fp)(x), a[i].b->c++, and calls returning callable expressions.

Declaration/expression ambiguity is scope-correct

Test typedef shadowing and multi-token type names in declarations, casts, sizeof, compound literals, and block-item starts.

Declarations and statements compose end-to-end

Parse translation units containing functions, nested blocks, labels, loops, conditionals, initializers, and complex declarators without recursive control flow.

Caller delimiters remain unconsumed

Verify semicolon, closing paren/bracket/brace, colon, and context-sensitive commas at top level and nested levels.

Malformed input never panics

Missing operands/operators/delimiters and invalid frame transitions must emit bounded diagnostics, synchronize, and unwind or reduce to an error node.

Both expression dialects share tested machinery

Preprocessor evaluation and AST expression parsing should use the same precedence-reduction core while retaining their distinct values, diagnostics, and legal operators.

Memory follows input nesting, not process stack depth

Stress tests should confirm bounded, inspectable heap growth proportional to active frames, operators, and operands.
